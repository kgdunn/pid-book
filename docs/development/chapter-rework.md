# Chapter rework playbook

A repeatable pattern for sweeping a chapter (or a numbered subsection) for
technical accuracy and reproducible figures. One chapter per PR, on the assigned
`claude/<slug>` branch, opened as a single non-draft PR against `main`.

`CLAUDE.md` carries the rules that hold in every session (the author's voice, the
executable-code contract, the citation bump). This file is only the order of
operations for a chapter sweep.

## Step 1. Read the section end-to-end

Note three categories as you read:

1. **Technical claims that depend on field knowledge**: measurement timing,
   sampling frequency, typical plant numbers, "every shift / once an hour"
   phrasing, instrument capabilities, method names.
2. **Figures that appear without code that would reproduce them.** A reader
   pasting the chapter top-to-bottom should be able to regenerate every plot.
3. **Internal inconsistencies and typos noticed in passing**, for instance a
   number that disagrees with itself across paragraphs. Fold trivial fixes into
   the same PR rather than opening a second one.

## Step 2. Fact-check the technical claims against external sources

**Do not take the chapter at its word, however authoritative it sounds.** The
book has been edited continuously since 2010, and some claims reflect
1990s-vintage equipment or older field practice. Run a couple of targeted
`WebSearch` / `WebFetch` queries per claim against current literature, vendor
documentation and standards, then revise the prose to match what the searches
show. Typical fixes:

- a worst-case anecdote softened to a typical range;
- an outdated method replaced or supplemented by the modern equivalent (an
  on-line NIR analyser alongside the wet-chemistry titration, say);
- a misremembered number corrected;
- a standard, instrument or vendor named so the reader can verify.

Anchor each revised claim to a named standard, instrument or vendor when one
exists (ISO 302 for the Kappa titration). The motivation for the chapter's
technique must still hold after the rewrite: just do not let it rest on a worst
case that turns out not to be typical.

## Step 3. Make every figure reproducible inline

For each `.. figure::` directive, insert a small `.. code-block:: python`
immediately before it.

- **Plotly only** in chapter code, as in the rest of the book: `import
  plotly.graph_objects as go`, `from plotly.subplots import make_subplots`. No
  matplotlib in learner-facing blocks.
- **Reuse names already defined earlier in the chapter.** It must read
  top-to-bottom as one linear script: no redundant data loads, no refitting the
  same model twice. Common imports go in the first block that needs them.
- **Define a helper once** when a plot type repeats, for instance
  `plot_obs_pred(...)` reused at two evaluation points.
- **Static PNGs stay generated by a matplotlib script** committed beside them in
  the same `kgdunn/figures` subdirectory (`monitoring/adaptive-softsensor-figures.py`
  next to the `monitoring/adaptive-softsensor-*.png` it writes). Those scripts
  import `process_improve` for the modelling but live in the figures repo. The
  chapter shows plotly code; the embedded image is the committed PNG. Touch the
  script only when the underlying analysis changes.

## Step 4. Verify before committing

1. `make check-code-chapter CHAPTER=<chapter-dir>`.
2. Every number the prose quotes (R², RMSEP, row counts, table values) must
   reproduce. Echo each one in a comment after the `print(...)` that produces
   it, so the checker compares it too.
3. `make text` must succeed with zero warnings.
4. `make html` must succeed, and `grep -r goatcounter _build/html/contents` must
   return zero hits.

## Step 5. Mechanics

- Bump `CITATION.cff` `date-released:` to today.
- Commit with a message about the *why*, and never name the model in it.
- Push to the assigned `claude/...` branch and open one non-draft PR per
  chapter. The body covers what changed, what did not, the headline numbers
  verified, and the results of the three commands above. If the underlying
  analysis is unchanged, say so.
- Subscribe with `mcp__github__subscribe_pr_activity`, then answer review
  comments and CI failures with small follow-up commits to the same PR.

## Pitfalls seen so far

- **A figure in section A ahead of the data load in section B.** Move the data
  load into A so the first figure's block stands alone, and shrink B's block to
  the modelling steps.
- **A helper that returned only what the prose needed** (`rmsep`) while the
  plotting blocks also need the y-vectors. Extend the signature once (`return
  rmsep, y_obs, y_hat`) and update every call site in the same commit.
- **A section reorder mid-PR.** The toctree change in `<chapter>/index.rst` is
  one line; before pushing, run `grep -rn -E '\b[0-9]+\.[0-9]+\b' --include='*.rst' .`
  to confirm no prose hard-codes the old numbers.
